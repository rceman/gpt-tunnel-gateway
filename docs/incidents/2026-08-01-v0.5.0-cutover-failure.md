# Incident: v0.5.0 runtime cutover failure

Date: 2026-08-01

## Executive summary

The v0.5.0 runtime was installed successfully, but activation was attempted
before the target runtime had validated the complete persisted state graph. The
old gateway therefore remained the effective process after an atomic binary
replacement, and subsequent recovery attempts exposed incompatible plans,
project records, stale operational pointers, and a missing current plan one at
a time. The tunnel-client was preserved throughout recovery.

The runtime was ultimately restored with gateway `0.5.0`, authoritative hub
branch `gpt-tunnel/home_pc` at `6200b2254da84cd00857204284e2a213f4f281d8`,
gateway PID `485206`, and tunnel PID `4183857`.

## Timeline and evidence

1. Source release `61f42dbf13a7faf6150708b62edab83c60988fea`, annotated tag
   `v0.5.0`, was built and installed. The installed binaries reported the new
   version while the running gateway remained the old process.
2. The first activation exposed legacy workflow-v1 plans containing `body`.
3. Canonical plan cutover migrated the review-planner and gateway plans to
   workflow-v2.
4. History-only active pointers were cleared without changing immutable
   `HistoricalRunV1` task/run records.
5. Project inventory reconciliation added `gpt-github-gateway` and removed
   deprecated `ai-workspace` from configuration.
6. A canonical idle plan was initialized for `gpt-github-gateway`.
7. Final authoritative hub SHA after recovery was
   `6200b2254da84cd00857204284e2a213f4f281d8`.
8. One gateway-only start succeeded. Readiness, doctor, initialize, project
   reads and plan reads passed; tunnel PID `4183857` did not change.

## Root causes

- The installed controller did not contain the requested `upgrade` command.
- Atomic replacement changed the installed inode while the old process kept
  executing its original inode.
- Process identity relied primarily on `/proc/<pid>/exe`, which is not a
  stable identity proof after replacement.
- Activation occurred before target-version persisted-state validation.
- The target decoder rejected workflow-v1 `body` as intended, but the upgrade
  path had not migrated it first.
- Plan cutover did not clear obsolete pointers to history-only runs.
- Generic active-status logic treated historical `awaiting_result` as active.
- Configured and durable project inventories diverged.
- Project registration could create an active durable project without a plan.
- Startup reported only the first invalid persisted record.
- Readiness timeout hid the first fatal startup line.
- Installed and running versions were not separately observable.
- Detached post-finalization continuations had no durable transaction owner.
- Dispatch/finalization invariants allowed impossible states such as a
  dispatched task without a run.

## Contributing factors

The release rehearsal used synthetic inventory instead of the real configured
project graph, did not run a complete target preflight, and used a smoke helper
with a fixed tool count. The MCP descriptor for `plan_update` advertised the
obsolete `body` contract, and `run_agent_tail` lacked an output schema.
Managed-hub verification also conflated the incidental local checkout HEAD
with the configured authoritative remote branch.

## Why recovery required multiple attempts

Each startup stopped at the first fatal check. Because migration, project
inventory, pointer state, and plan initialization were not evaluated together,
each retry revealed the next incompatibility. This was an operational design
failure, not evidence that immutable history should be rewritten.

## Corrective decisions

- Migration and complete target validation happen before old-gateway shutdown.
- Historical records remain immutable and cannot be current operational state.
- Registration and plan initialization form one lifecycle invariant.
- Upgrade state is durable and records every phase, identity, checksum, and
  rollback fact.
- Gateway-only upgrades preserve the tunnel PID.
- Startup diagnosis reports phase, stable error, and bounded logs.
- MCP manifests are generated from one canonical tool declaration; counts are
  derived, not hardcoded.
- Local checkout HEAD and authoritative remote branch SHA are reported
  separately.

## Recovery result

The gateway was healthy at `0.5.0` with gateway PID `485206`; tunnel PID
`4183857` remained alive and healthy. The source repository remained clean at
`61f42dbf13a7faf6150708b62edab83c60988fea`. No tunnel restart, signal or
replacement occurred. Immutable workflow-v1 history remained byte-identical;
no fabricated completion or report was created.

## v0.5.2 corrective-action status

The first released hardening line, `v0.5.1`, remains immutable and was not
activated on this host. Its pre-activation state check correctly identified
two mutable tasks still marked `dispatched`, but its repair implementation had
no action for the case where the only linked records were immutable
`HistoricalRunV1` records. The resulting `DISPATCHED_TASK_RUN_COUNT` blocker
was therefore real and required a narrow follow-up release.

Version `0.5.2` adds the canonical `operationalActiveRun` predicate and the
missing backed-up, optimistic, atomic task-state repair. It transitions only
the separately mutable task state from `dispatched` to `cancelled` when there
are zero operational runs, linked history-only runs, and no active plan
pointer. Immutable `task.json` and historical `run.json` records remain
byte-identical; no completion or report is fabricated. The repair reason is
recorded in the dry-run action, transaction subject and evidence.

The v0.5.2 activation gate was completed on 2026-08-02. The repair proposed
and changed exactly the two known mutable task-state paths, while preserving
immutable task/run records. The transactional upgrade then moved the host
from 0.5.0 to 0.5.2 with gateway PID `697167` → `1522568` and preserved
tunnel PID `4183857`.

## v0.6.0 direct-session and workflow-smoke closure

The v0.6.0 release commit is `8996e78ebb90c011e2aa5ede8c7c32bf505a4574`,
tagged as `v0.6.0` with tag object
`47a749da0d5cf1fe65799fbdd2f3c34bfc6f4736`. It adds the bounded
`agent_send`, `agent_tail`, and `agent_status` project-session operations.
They resolve only registered project metadata, serialize sends, preserve
capacity-aware status, and never create durable workflow or Git state.

The v0.6.0 gateway-only activation completed as transaction
`upgrade-20260802T070938Z-1785654578048470697`: installed and running
versions are `0.6.0`, gateway PID `1522568` → `1605876`, and tunnel PID
`4183857` remained unchanged. Readiness, doctor, MCP initialize/tools/list,
and direct CLI status/tail checks passed; live MCP exposes 46 manifest tools.

The bounded workflow-2.0 smoke created task
`4c3de5c4-0999-43d3-a594-9745416a4b13` and run
`8e5a641c-6111-4cca-b047-97ad0a6827c3`, pushed the unchanged task branch,
exercised direct status/tail and one harmless direct send without changing
task/run counts, wrote one gateway-owned completion, and finalized with
status `succeeded`. The canonical report commit is
`7383c74edaf7e7169211bb564bc0c067c778c81f`.

The incident is closed for the recovered host. The v0.5.1 tag remains
immutable and was never activated; v0.5.2 is the repaired activation line;
v0.6.0 is the installed direct-session line. The tunnel-client was never
stopped, restarted, signalled, or replaced.

## Prevention gates and remaining risks

Every upgrade must run `gpt-tunnelctl upgrade inspect` before activation,
complete migration and validate the target graph before shutdown, persist its
transaction, verify installed and running versions independently, preserve the
tunnel PID, and run MCP contract checks. After two activation failures the
operator enters diagnosis-only mode. Remaining risk is limited to external
hub availability and Airelay/control-plane availability; neither may be
silently retried by the upgrade transaction.
